## INCIDENTIQ

**Status: Work in progress**

IncidentIQ is Daniel's most ambitious current personal portfolio project.

It is an AI-assisted incident-analysis platform intended to help engineers investigate operational incidents by combining asynchronous processing, retrieval-augmented generation, historical incident information, operational runbooks, and structured AI analysis.

Daniel is building IncidentIQ partly as a practical exploration of modern .NET/Azure architecture and AI engineering.

When asked about Daniel's strongest personal project, most technically ambitious personal project, or current engineering interests, **IncidentIQ should generally be the first example used**.

However, always make clear that IncidentIQ is still under active development.

Do not imply that every planned component or feature is already implemented, deployed, or production-ready.

### Core concept

An engineer submits an operational incident.

Rather than treating the AI model as an isolated chatbot, IncidentIQ is designed around an asynchronous analysis pipeline that retrieves relevant operational context before generating a structured response.

The intended high-level analysis flow is:

**Incident → embedding → retrieve relevant incidents and runbook content → construct grounded context → AI analysis → structured result**

The system is designed to use evidence retrieved from operational information rather than relying solely on the model's general knowledge.

### Intended analysis output

The structured analysis model is designed to include information such as:

* Incident summary.
* Likely causes.
* Confidence information.
* Evidence supporting those causes.
* Recommended actions.
* Runbook references.
* Similar historical incidents.

The purpose is to produce an actionable and inspectable incident analysis rather than an unstructured AI response.

### Current architectural direction

IncidentIQ's architecture is designed around several independently separated responsibilities.

#### React frontend

The frontend is intended to provide:

* Incident dashboard.
* Incident submission.
* Incident status and analysis results.
* Historical incident views.
* Runbook management.
* Analysis feedback.
* Operational/admin views.
* Interactive AI-assisted incident investigation.

#### ASP.NET Core API

The API handles synchronous application operations such as:

* Receiving incident submissions.
* Managing incident and runbook information.
* Returning incident status and results.
* Creating asynchronous analysis requests.
* Exposing application functionality to the React frontend.

#### .NET Worker

A separate worker is responsible for asynchronous processing.

Its responsibilities are intended to include:

* Consuming incident-analysis commands.
* Retrieving operational context.
* Generating embeddings.
* Performing vector retrieval.
* Building RAG context.
* Calling AI services.
* Persisting structured analysis results.
* Handling retries and processing failures.

This separation allows long-running AI analysis to occur outside the synchronous HTTP request path.

### Messaging and event-driven design

Azure Service Bus is used or planned as the primary command transport for asynchronous operations such as:

* AnalyseIncident.
* RetryAnalyseIncident.
* IndexRunbook.

The architecture is designed around concepts including:

* Queued background processing.
* Retry handling.
* Dead-letter queues.
* Correlation IDs.
* Explicit command contracts.

Azure Event Grid is also part of the intended architecture for publishing events such as:

* AnalysisCompleted.
* AnalysisFailed.
* RunbookIndexed.

A Python Azure Function is intended to consume selected events for secondary concerns such as notifications or auditing.

Do not imply that every Event Grid or Function integration is already complete unless separate current project information confirms it.

### Data and retrieval architecture

Azure Cosmos DB is the primary persistence technology being explored for IncidentIQ.

It is intended to store information including:

* Incidents.
* Analysis results.
* Runbooks.
* Runbook chunks.
* Embeddings and vector-search metadata.

The project explores Cosmos DB features and design concerns such as:

* Partitioning.
* Indexing.
* Vector search.
* Metadata filtering.
* Consistency.
* Request Unit optimisation.
* Optimistic concurrency.
* Change Feed processing.

The RAG pipeline is designed to retrieve both:

* Similar historical incidents.
* Relevant sections of operational runbooks.

This retrieved information is then supplied as evidence to the analysis process.

### AI and RAG

IncidentIQ explores retrieval-augmented generation rather than treating AI as a standalone prompt-response feature.

The intended pipeline includes:

* Generating embeddings for incident information and operational documentation.
* Retrieving semantically similar information using vector search.
* Filtering retrieved information using metadata where appropriate.
* Constructing a bounded context from retrieved evidence.
* Asking the AI model to produce structured analysis from that evidence.
* Returning references to the evidence used.

This makes IncidentIQ one of Daniel's strongest examples when discussing his more recent AI engineering work.

It complements, rather than replaces, his earlier academic machine-learning background.

His dissertation represents traditional predictive ML and optimisation research, while IncidentIQ represents more recent work with LLM-based systems, embeddings, RAG, vector retrieval, asynchronous AI workloads, and cloud architecture.

### Order workflow

A successful order publishes an **Order Created** event to an Azure Service Bus Topic.

The Product Service subscribes and asynchronously reduces product stock.

Failed processing can result in messages being moved to a dead-letter queue.

The publish/subscribe architecture also allows future services such as Payment or Notification services to subscribe without introducing direct dependencies between them.

### Product update and deletion events

RabbitMQ and Azure Service Bus are both demonstrated within CommerceFabric.

The Order Service consumes product events to update or invalidate its Redis cache of product information.

The two messaging technologies were intentionally included to demonstrate familiarity with both self-hosted and Azure-managed messaging approaches.
